# Agent guide — Settleview (repo: btc-flow-engine, to be renamed settleview)

Instructions for coding agents (Codex, Claude Code, others) working in this repo. Read this first, then
`docs/research/LEARNINGS.md` before proposing or testing any trading idea.

## What this repo is

A local app for short-window Bitcoin up/down markets (Kalshi KXBTC15M; Polymarket US 15m and 5m): one Play screen
(live data, the market's and our model's read, human-approved trading on your own accounts) and an offline research
toolkit (`scripts/`, `docs/research/`). There are no bots and no strategy lab in the app (removed 2026-10-29); a
strategy idea is tested offline first. Agent mode (2026-10-30) is the one exception to "no automation": an AI agent
trades only inside a bounded session the user launched (budget, per-trade cap, end time, venues, API cap), and every
agent order goes through the same prepare -> OrderGate -> approve path as the human's slide, never around it.
Hexagonal layout (`domain/` pure, `application/` uses ports, `adapters/` do I/O, `bootstrap/` wires) enforced by
`lint-imports` (a test in the suite). Plans live in `docs/plans/`, research in `docs/research/`.

## Hard rules (never break these)

1. **No real money.** Never place, amend or cancel orders on Kalshi production or demo, never call trading
   endpoints, never change a trading mode, never touch the live app on :8000 / :8001 (the Docker
   stack run from the owner's separate deploy checkout) or POST to it. The owner's local, untracked
   `CLAUDE.local.md` names that checkout on their machine; read it when it exists.
2. **Never read, print, copy or send `.env`, `key.pem`, `*.pem`, or any key id / key path.**
3. **Research databases are read-only.** Open `data/btcflow.db` and `data/research/*.db` only with the SQLite URI
   `file:...?mode=ro`. Write only new files under `data/research/` and `docs/research/`, `scripts/`.
4. **No mock or fake data in the app** (`web/`, `btc_signal_engine/`). Tests may build their own data.
5. **No git pushes.** Coding agents and subagents never push (and never touch the local-only `archive/*` tags).
   Commit only when asked, with a clear message. GitHub's `main` (`origin`) is the source of truth; only the owner's
   own main session pushes, and only with the owner's approval (docs/PUBLISHING.md, "How a change reaches GitHub").
   Every commit uses the GitHub no-reply address as author and committer (this clone's `user.email`; check it in a
   new worktree). The pre-push hook (`git config core.hooksPath .githooks`; `scripts/prepush_scan.py`) refuses
   archive tags, other emails, personal paths and addresses, and secrets; never bypass it with `--no-verify`.

## Docs are part of done

This repo is meant to be published on GitHub with a best-in-class product, marketing and developer experience
(user, 2026-10-31). A change is not finished until its docs are:
- `README.md` — the product page: what it is, what it isn't, feature list, screenshots, quickstart. Update the feature
  list and screenshots when a user-visible feature changes. Keep the honest framing (no edge claimed; risk stated).
- `docs/api.md` for any route added or changed (method, path, body, response, PC-only, errors).
- `docs/operations.md` for any setting, env var (name and purpose only — never a value), deploy or runbook change.
- `CHANGELOG.md` — one line per user-visible change under "Unreleased".
- Screenshots in `docs/images/` are generated by the e2e tests (phone and desktop, light and dark); never
  hand-edited, never showing real balances, account ids, keys or order ids.
- Follow `docs/PUBLISHING.md` before anything goes public.

## Quality gates are part of done

Any change to code, the image (Dockerfile, compose, `deploy/`) or dependencies is finished only when the quality gates
are green (user, 2026-10-31): `python scripts/dev.py quality` (`scripts/quality.py`: Ruff, Hadolint, ShellCheck,
and Trivy on the rebuilt image, the config and the repository's secrets; CI runs the same script). Fix a finding rather than
silencing it; a `# noqa` names the rule and the reason, a `.trivyignore` entry has a reason, a date and an expiry
(docs/operations.md, "Quality gates"). Don't run `ruff format` over the codebase: that one-time reformat is its own
decision.

## Learnings are part of done

Every action should leave the project smarter (user, 2026-10-31). After any build, test, deploy or live run:
- Trading and research results (live or backtest, wins and losses) go into `docs/research/LEARNINGS.md` with n,
  win % vs break-even, net per contract and a verdict — the existing honesty rules apply.
- Engineering lessons that the code and tests don't already explain (a root cause, a venue/API quirk, a decision and
  why, something that wasted time) go into `docs/solutions/` as one short file each (problem, cause, fix, how to
  avoid), linked from the relevant doc.
- Don't record what git history or the code already says; record what the next agent would otherwise rediscover.

## Runtime (default for local development and production)

Docker Compose is the default way to run Settleview, locally and in production (user, 2026-10-31): one image, the
same `compose.yaml` (app, Postgres 17, the one-off `migrate` job, `rec-pm-quotes`, `rec-pm-settle`, `backup`; `openobserve` with the opt-in
`observability` profile), Linux containers on any host
(Docker Desktop on Windows/macOS, a Linux server or Swarm; Azure Container Apps / AWS with managed Postgres). Don't
add host-specific behaviour (Windows-only scripts, `C:\` paths, arch-specific defaults); the live host is just one host.
- The live stack runs from a separate deploy checkout (not this one) as compose project `settleview` (volumes
  `settleview_settleview-{pg,data,backups}`); the PC uses http://localhost:8001 in a browser paired with
  `ops pair-pc` (no PIN), phones :8000 (PIN), external agents :8002 (session token). Never pair against or call the
  live stack from an agent session.
- Deploy: the deploy checkout is a worktree of the dev clone, so `git -C <dev clone> fetch origin`, then `git
  checkout <sha>` (a commit on `origin/main`) in the deploy checkout, `docker build --build-arg GIT_SHA=$(git rev-parse HEAD) -t
  settleview:local .`, `docker compose up -d`
  (a restart of `app` ends agent sessions: only between sessions). Build from the real-case path (`Documents`).
  Secrets are files in `./secrets` (compose secrets), never `.env` lines; the one-time move is
  `python deploy/secrets_from_env.py` (docs/operations.md, "Docker: secrets as files").
- Agents and scripts never connect to the live database for writes; research reads use the `settleview_research`
  role (read-only by permission).
- The SQLite files under `btc-flow-engine/data/` were the pre-2026-10-31 store: kept read-only as the rollback until
  2026-11-07, then archived.

## Environment

Containers for everything: development, tests, quality gates, research scripts, experiments, evals and the README
screenshots run in Linux containers, as production does. There is no host virtualenv. The host needs Docker and any
Python 3 (or just uv: `uv run --no-project python scripts/dev.py ...`, which uses uv's interpreter and creates no
environment); `scripts/dev.py` (standard library only) drives the dev container (`deploy/dev/`, compose project
`settleview-dev`, never the live `settleview` stack). The checkout is bind-mounted, so edits need no rebuild:

- Tests: `python scripts/dev.py test` (the whole suite, e2e in Playwright's Chromium; any pytest arguments after it;
  check pytest's own exit code). Import contracts are part of it (`tests/architecture`); alone:
  `python scripts/dev.py quality --only imports`.
- Postgres: `python scripts/dev.py postgres-tests` (the `postgres`-marked tests on a throwaway Postgres 17; none may
  skip; `--full` then runs the whole suite on it).
- Quality gates: `python scripts/dev.py quality` (Ruff and lint-imports in the dev container; Hadolint, ShellCheck and
  Trivy in their own pinned containers, as CI).
- Research: `python scripts/dev.py experiments <run|grid|report|selftest> ...` and `python scripts/dev.py script
  <path> [args]` run a script with the checkout read-only, `data/` read-only, `data/research/` writable for new outputs
  (and the `experiments_results.csv` append) with every database in it read-only, and `docs/research/` writable.
  `--data DIR` points at another checkout's `data/` (a worktree has none).
- Evals: `python scripts/dev.py evals test` (what CI runs), `evals run pipelines/pr.toml`, `evals graders`,
  `evals export|review ...` (`data/` mounted read-only).
- Anything else: `python scripts/dev.py run <cmd>` or `shell`. A second checkout (a worktree) running alongside sets
  `SETTLEVIEW_DEV_PROJECT=settleview-dev-<name>` so the two never share a test Postgres.

The host's CPU or OS never shapes a dependency: one pin per package, no platform markers. Do not add packages without
the user's OK. Dependencies install from the hashed `uv.lock`: after changing a pin in pyproject.toml, run
`python scripts/dev.py run sh -c "UV_CACHE_DIR=/tmp/uv uv lock"` and commit both (docs/operations.md, "The lock file"). The research data exists only on the machine that recorded it (`data/` is git-ignored).

## Venue APIs

- **Polymarket US: use the official `polymarket_us` SDK for every call** (REST and WebSockets), never hand-rolled HTTP or
  signing. Prices come from the WebSocket only (the REST BBO is a ~30 s cached snapshot); one subscription per market,
  at most 10 subscriptions per connection (observed 2026-10-29; undocumented) — the markets stream pools connections at
  3 markets x 3 types each. Positions lag our fills: trust our own fills briefly, then the positions list.
- **Kalshi:** the repo's adapters (`adapters/kalshi/`); WebSocket primary, REST polling as backup. Kalshi REST goes
  through the official `kalshi_python_async` SDK underneath our adapters (`adapters/kalshi/backend.py`): our guards
  (series allow-list, notional cap, signing allow-list) run in front, our own retry loop is the only one (the SDK's
  retries are off), and requests are signed by our auth objects (not the SDK's). The WebSocket stays ours (the SDK has none);
  the shadow exchange keeps its in-memory httpx transport.
- **Kalshi perps (exception):** the SDK has no margin endpoints, so `adapters/kalshi/margin.py` is our own httpx
  client with the same rules: our retry loop is the only one (same `client_order_id`), the transport resends nothing,
  redirects are not followed, idle sockets drop at 30 s. Its signer (`MarginAuth`) has its own allow-list, signs for
  its env's host only, and never signs cancel-all, subaccount create or transfer, or any `/margin/isolated/*` path.
- **Signing:** every Kalshi credential is a `KalshiSigner` (`adapters/kalshi/auth.py`): its own allow-list plus pinned
  hosts (https, default port), checked in httpx's `auth_flow` and the SDK's auth hook alike. Never sign by hand.
- **One rule per figure:** a bracket's net and stop (`domain/brackets.py`), money/cents/side text (`domain/fmt.py`;
  the browser's `fmt.*` in `web/app.js`), venue date-times (`domain/timestamps.py`), a stored setting
  (`application/settings_store.py`) and retry waits (`adapters/retry.py`) each have one function; use it.

## Running experiments

The harness is `scripts/experiments.py` (read its module docstring — it defines the honesty rules). `python` below
is any environment with the project installed (`python scripts/dev.py shell`, or a native venv).

```bash
python scripts/experiments.py selftest
python scripts/experiments.py run --entry h6_favourite_75_90:lo=75,hi=90 --exit hold,sl10
python scripts/experiments.py report
```

Add an idea as one decorated function in `scripts/experiments.py`:

```python
@entry_rule("my_rule")
def my_rule(D, x=1):   # D.YA/YB candles, D.F model fair odds, D.btc(t), D.strike, D.indicator("rsi", t)
    ...                # return (decision minute index k, side) arrays for every window; side 0 = no trade
```

Exits are named specs (`hold`, `sl10`, `tp20`, `trail10`, `time1`, combinations like `mtp20_bstop20`); see
`parse_exit` in the script. Every configuration you run is appended to `data/research/experiments_results.csv`
and counted in the multiple-testing correction — that is intentional; do not delete rows or reset the count.

## Honesty rules for research (how to not fool yourself)

- **Write the rule and the pass/fail bar before looking at results.** Turn vague advice into an exact rule and say
  how you interpreted it (in the rule's docstring).
- **Scoring is fixed:** entries only at prices that really traded, 1¢ slippage primary, exact Kalshi taker fee
  (0.07·C·P·(1−P) rounded up to $0.0001; makers 0), Kalshi's official result, one trade per window, t clustered by
  window. Do not change the harness's scoring, splits or fee code to make a rule look better.
- **Train on the first 20 days, judge on the holdout (last 10).** A rule "survives" only if its holdout result
  clears the correction the report prints (Bonferroni across all configurations tried), is positive in both
  chronological halves, and has at least 30 holdout trades.
- **The holdout is not a tuning set.** Do not iterate parameters against it. If you must tune, tune on train only,
  then run the frozen rule once on the holdout.
- **A survivor is a CANDIDATE, not a strategy.** Report it; it then needs a check on new data (days after the
  current dataset) and a shadow run before anyone risks a cent.
- **Win rate means nothing without the price paid.** Always report win % next to break-even %.
- **Negative results are results.** Most ideas lose about the cost of trading; record them.

## Record every result

After any experiment, update `docs/research/LEARNINGS.md` (the hypothesis register): one row per idea with the
verdict (KILLED / OPEN / CANDIDATE / inconclusive), the key numbers (n, win %, break-even %, net ¢/contract, t on
the holdout) and a link to the evidence. Check the register first so nothing is re-run without a reason.

## What is already known (short version — details in LEARNINGS.md)

- Kalshi's 15m BTC prices are well calibrated; our random-walk model adds no information beyond the market price.
- Forced entries, aggressive settings, stop-losses and take-profits all lose about the cost of trading.
- 17 popular human rules and 8 named Reddit/YouTube/GitHub strategies have been tested; none survives.
- Killed since: contract-price momentum (H8: interim +12.9¢ was noise, final −3.0¢), longer-horizon markets and
  options-implied volatility, the LLM trader's first rules (see docs/research/llm-trader-loop.md).
- Open leads: market making (live data only — cannot be backtested; the app's shadow lab that measured it was removed
  2026-10-29, its recorded rows stay in the database); H4 (BTC ±0.4% from the strike
  3–5 min in, buy that side) is weakening: 27/27 over the first 30 days, but on Oct 29–30 it fired in 6.7% of windows
  and won 11/12 against a 91–92% break-even (about 0¢/contract). H4 and EXP-CUSHION100 are being forward-tested live
  at $1 by the agent (Agent mode); see LEARNINGS.md.
- Agent mode (2026-10-30): bounded agent sessions trade through the same order gate as the slide; the old "no bots"
  rule now means no unbounded automation — every agent order is inside a session the user launched, with its limits.
